Capabilities

The hard parts of running WordPress, already solved.

Most "managed WordPress" hosts hand you a faster shared box and a caching plugin. We hand you a real Kubernetes platform — page caching, scaling, DNS, secrets, and rollouts engineered at the infra layer, not bolted on with a plugin.

Page cache that never touches PHP

Nginx + srcache + Lua serve hot pages straight from Memcached or Redis in single-digit milliseconds. Cache misses spawn a single backend request and refill the cache atomically. No WP plugin, no wp-content/cache, no nightly cache purges that nuke your site.

Four PHP versions, one runtime

PHP 8.1, 8.2, 8.3, 8.4 — purpose-built runtime images for each. Pin per site. Upgrade one site without touching the rest of the fleet. Canary the new minor on staging, then promote the same image tag to prod.

Cluster-native DNS, the way it should be

Configurable nginx resolver. Point it at your cluster DNS (10.96.0.10), and every proxy_pass resolves cleanly to internal services. No more hardcoded 8.8.8.8 like the upstream stacks still ship with.

GitOps-native, top to bottom

A site is a Kubernetes Wordpress CR. Commit it. Let Argo CD or Flux apply it. The operator reconciles Deployments, Services, Secrets, and PVCs to match. No dashboards. No drift. No "who deployed what at 4pm Friday".

Composer-first, Bedrock-style codebase

Sites are real PHP projects, not folders someone FTP'd up at 2am. Plugins, themes, and core are pinned in composer.json, locked via composer.lock, and reviewed in pull requests — supply-chain provenance is real. composer require wpackagist-plugin/yoast-seo adds a plugin; docker-compose up boots the same image locally. Zero drift between dev and prod.

Secrets that aren't on a server

Database credentials, API keys, OAuth tokens — everything sensitive lives in Kubernetes Secret resources, mounted into the pod at runtime. Not in wp-config.php. Not in a plaintext .env on a server. Not in your git history. Rotate via kubectl or your existing manager (Vault, AWS Secrets Manager, GCP Secret Manager) — SOC 2 evidence collection becomes a one-screenshot exercise.

Gateway API + your edge of choice

Routing is decoupled by design. Point an HTTPRoute, an Ingress, a Cloud Load Balancer, or your existing CDN at the Service the operator generates. Your platform team keeps owning the edge — we don't try to take it.

Any Kubernetes, anywhere

Same operator, same runtime — runs on EKS in London, GKE in Frankfurt, AKS in Dublin, your bare metal in Reading, or k3s on a Pi if that's what you've got. Bring your own cluster, or use ours. WP Engine and Kinsta lock you to a single hyperscaler; we don't.

Cloud-native media offloading

Stop pre-buying disk "just in case". Every site offloads uploads, attachments, and editorial assets to Google Cloud Storage — 99.999999999% durability (eleven nines), multi-region availability, single-digit-ms first-byte from any continent. No disk-space markups when next month's campaign drops 80 GB of hero video. Storage scales independently of compute; your invoice doesn't lurch every time the editorial team gets ambitious.

Why it's faster

Faster than "managed WordPress" because it isn't.

Most hosts measure WordPress performance from inside PHP. We refuse to enter PHP at all unless we have to. That's where the speed comes from — not a marketing slide.

01

The cache is in nginx, not in WordPress.

Plugins like WP Rocket cache after WordPress has already loaded — every request still spins up PHP-FPM, parses 50+ plugins, and connects to MySQL. We cache before WordPress. Hot pages skip PHP entirely. Cold pages refill the cache in one trip.

02

Replicas scale horizontally, like real software.

Traffic spike? Bump spec.replicas, or let the HPA do it for you. The operator rolls new pods, the Service fronts them, the cache stays warm across replicas because it's external. No "upgrade your VM" downtime. No five-minute IIS reboots.

03

Config is generated at startup, from your environment.

Dockerize templates render nginx + PHP-FPM config at container boot from spec.env. Want a different cache backend? One env var. Different upload limit? One env var. No SSH, no nginx -s reload, no config drift between staging and prod.

04

It's open source, so you can prove every claim on this page.

Three repos. wordpress-operator & wordpress-runtime are Apache 2.0; wordpress-site-template is MIT. Read the controller code. Read the nginx templates. Run it on your own cluster and pay us nothing. We're confident enough to compete on operations, not lock-in.

Frequently asked

Answers to the questions enterprise buyers actually ask.

Where does my site actually run?

On a managed Kubernetes cluster — ours, or one in your own cloud account. Either way you get the same operator, the same runtime images, and the same upgrade path. No proprietary control plane, no escape hatch you can't open.

Can we keep our existing themes and plugins?

Yes. We ship a Bedrock-style site template that uses Composer for plugin management, but you can run any standard WordPress codebase — custom plugins, premium themes, mu-plugins, drop-ins. One thing changes: in production the filesystem is read-only, so plugins enter through pull requests and code review, not through wp-admin uploads. That removes one of WordPress's largest attack surfaces by default.

What does our developer workflow look like?

Standard Composer. composer require wpackagist-plugin/<name> adds a plugin; you commit composer.json and composer.lock; the next image build picks it up; the operator rolls it to production. docker-compose up boots the exact same runtime image locally for development. Code review runs through your existing GitHub or GitLab process. The Wordpress custom resource lives alongside your application code in a Helm chart or Kustomize overlay — infrastructure ships through the same PRs as code.

How are secrets and credentials handled?

As Kubernetes Secret resources, mounted into the pod at runtime as environment variables — never written to disk in wp-config.php or a .env file. Rotate them via kubectl, the External Secrets Operator (pulling from Vault, AWS Secrets Manager, GCP Secret Manager), or Sealed Secrets / SOPS for fully GitOps-encrypted workflows. Access is governed by your cluster's RBAC, and every read is auditable. None of this requires a WordPress plugin.

Where do uploads and media files live?

Off the application disk, in Google Cloud Storage. WordPress reads and writes through a stream wrapper, so wp_upload_dir(), the media library, and any plugin that calls wp_get_attachment_url() all just work — they get a CDN-fronted GCS URL instead of a local path. Eleven nines of durability, no filesystem-locking surprises during deployment, and pod restarts no longer lose unsynced media. Storage allowances are bundled into each tier (100 GB on Growth, 1 TB on Business Critical, 3 TB+ on Elite HA); overages are billed at our cost, not marked up.

How do migrations work?

We import your existing site (database + uploads + codebase) into a staging environment running on our stack, run the diff against your live site, and cut over with DNS. Most migrations finish in a single business week.

What's the SLA?

99.95% on Business Critical, 99.99% on Elite HA — both measured at the application layer (TTFB on a cached request), not just at the load balancer. Credits are automatic and posted on the next invoice in GBP, net of VAT.

Will I get hit with traffic-overage charges?

No. We bill the resources you provision (CPU, RAM, storage), not the visitors who arrive. WP Engine and Kinsta meter visits and charge per 1,000 over your cap; we don't. A viral post, a Black Friday spike, or a cited piece of journalism won't generate a surprise invoice.

Where is the infrastructure hosted?

Wherever you have a Kubernetes cluster. Our default managed offering runs on dedicated UK bare metal we own and operate — best performance-per-£ for editorial and WooCommerce workloads, zero noisy-neighbour CPU steal, no hyperscaler egress charges. But the same operator and runtime deploy unchanged to EKS, GKE, AKS, OpenShift, Rancher, or your existing on-prem cluster. On Elite HA we'll provision into your VPC if procurement requires it — your security perimeter, your audit logs, your IAM. WP Engine and Kinsta lock you to a single hyperscaler; we don't.

If it's open source, why pay you?

Because running stateful workloads on Kubernetes on call at 2am is its own job. You're paying for the operations, the SLA, the response time, and the years of WordPress edge cases we've already handled. The code stays free either way.

Do you offer SSO, audit logs, and data residency?

On the Enterprise tier, yes — SAML / OIDC SSO, immutable audit logs, and region-pinned data residency including EU-only options for GDPR-sensitive customers.
